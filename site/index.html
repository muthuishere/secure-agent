one static Go binary · no daemon · no SaaS

Your agent uses the key.
It never sees the key.

Coding agents need credentials and are the worst possible place to put one — every value they touch lands in a transcript, a prompt cache, a log, a commit. sec hands the agent a placeholder instead. It fills {{NAME}} at the moment of execution, in a child process, and scrubs the value back out of everything that comes home.

Install Watch the 4-minute demo

One unbroken Claude Haiku 4.5 session against a throwaway vault. Every command in this film was issued by the agent, not typed by a human. It leaks the key doing an ordinary job, gets stopped by the harness, then does the same work through sec — generating, rendering, tracking, rotating and auditing a credential it is never allowed to see — and finally tries to get the value back out through base64, a hex dump and fold -w 12, and can't.

a real session — output below is copied verbatim
# the agent writes this. It has never read STRIPE_KEY and cannot.
$ sec exec -- sh -c 'echo "key is {{STRIPE_KEY}}"'
key is [REDACTED:STRIPE_KEY]

# same for env-var injection
$ sec run STRIPE_KEY -- sh -c 'echo "env: $STRIPE_KEY"'
env: [REDACTED:STRIPE_KEY]

# the value re-encoded on the way out
$ sec exec -- sh -c 'printf %s {{STRIPE_KEY}} | base64'
[REDACTED:STRIPE_KEY]

# and re-encoded *and* wrapped — one character per line, the worst case
$ sec exec -- sh -c 'printf %s {{STRIPE_KEY}} | fold -w 1'
[REDACTED:STRIPE_KEY]

The real key went to the child process. What came back to the model is a label. Redaction covers the raw value and its base64 (with and without trailing newline), hex, URL-encoded and JSON-escaped forms — because a leak rarely comes out in the shape it went in. Matching is newline-tolerant: ordinary tools wrap long output — xxd -p at 60 columns, GNU base64 at 76, fold wherever you ask — and a value that comes back in three pieces is still the value, so the stream is searched with the line breaks removed too.

the problem

A secret doesn't leak once. It leaks everywhere it was copied.

The agent era didn't invent credential sprawl. It industrialised it — a value pasted into a prompt is now in a transcript, a cache, a summary and three files nobody kept track of.

without sec

The value is in the conversation

You paste the key so the agent can test the endpoint. It's now in the request body, the response, the session log on disk, the commit the agent made "to save progress", and the summary it wrote when the context compacted. You can't un-paste it — you can only rotate it, and you don't know everywhere it went.

~/.claude/projects/…/session.jsonl   ← it's in here
git log -p                            ← and here
.env.dev, conf.yaml, CI, the ticket   ← and here
with sec

The value is in a child process, for 40ms

The agent writes {{STRIPE_KEY}}. sec decrypts, substitutes, execs, scrubs stdout and stderr line by line, and writes one audit line naming the secret — never the value. The harness itself refuses sec get, so the refusal isn't the model's good behaviour, it's a deny rule the model cannot argue with.

transcript   [REDACTED:STRIPE_KEY]
audit.ndjson exec STRIPE_KEY claude-code
vault        STRIPE_KEY.age (ciphertext)
how it works

Three moving parts, none of them a server.

01

An age-encrypted vault

~/.config/sec/vault/NAME.age — X25519 via filippo.io/age, plus a NAME.json of metadata. Ciphertext and names only, so the directory is safe to commit to a private repo or rclone sync. Sync is deliberately not sec's job.

02

A pluggable identity

The same three backends Bun.secrets gives JS, plus a file: SEC_IDENTITY (CI) > OS keyring > identity.txt (0400). macOS and Windows default to the keyring; Linux defaults to the file, because a server has no Secret Service and a desktop one is DBus that can block forever on a prompt nobody is there to answer.

03

An owner check with no model in it

A TTY on stdin — or an explicit SEC_OWNER=1 — is the owner. Agent harnesses run with a piped stdin, so they never have it. get --print, export and every output-only path fail by construction, not by persuasion.

past the env var

Most brokers can only fill an environment variable.
Half of real config isn't one.

A TLS key in a YAML file. A token in a CLI argument. A service-account JSON a tool reads by path. exec and render cover the shapes doppler run and op run structurally cannot.

verbatim session
$ cat conf.tmpl
db:
  password: {{APP_DB_PW}}
  stripe: {{STRIPE_KEY}}

$ sec render conf.tmpl --out conf.yaml
✓ rendered conf.tmpl → conf.yaml (0600; 2 secret(s), placement recorded)

$ sec gen --save APP_DB_PW --len 32 --env .env.dev=DB_PASSWORD
✓ DB_PASSWORD written to .env.dev (0600)
✓ APP_DB_PW stored (v1, 32 chars)

The generated password was never printed, never in argv, never in the agent's context — and the output file is 0600. "placement recorded" is the part that pays off next.

the compromise-day question

"Where did this key end up?" should be one command, not an afternoon.

Every write — env write, render, import, gen --env, place — records a placement. Rotation replays the ledger instead of asking you to remember it, and prints the steps a tool honestly cannot do for you.

verbatim session
$ sec rotate APP_DB_PW --gen
✓ APP_DB_PW v1 → v2
  ✓ file   .env.dev  (DB_PASSWORD)
  ✓ render conf.yaml  <- conf.tmpl

MANUAL steps:
  ⚠ the generated value was NOT applied at the source (no --hook) — apply it there, or `sec rotate APP_DB_PW --undo`
  ⚠ restart whatever reads .env.dev
  ⚠ restart whatever reads conf.yaml
  · when the old value is revoked: sec rotate APP_DB_PW --purge

$ sec where APP_DB_PW
APP_DB_PW  v2  updated 2026-09-19 13:38
placements (2):
  file   .env.dev  (DB_PASSWORD)   [2026-09-19]
  render conf.yaml  <- conf.tmpl   [2026-09-19]
retired versions still to revoke upstream: v1(09-19)   → `sec audit --retired`, then `sec rotate NAME --purge` once revoked
activity in the last 30 days (3):
  09-19 19:08  rotate    claude-code
  09-19 19:08  render    claude-code
  09-19 19:08  gen       claude-code

Give it --hook hooks/postgres-rotate.sh and the source is rotated too — the hook receives SEC_NAME, SEC_NEW_VALUE and SEC_OLD_VALUE in its environment, so the value never reaches argv. hooks/ ships Postgres and AWS IAM to copy. Note what it refuses to claim: an old version stays listed as "still to revoke upstream" until you tell it the revocation actually happened.

the surface

Twenty verbs. You will use six.

sec setStore a value from stdin — masked prompt on a TTY, never argv.
sec execRun a command or script with {{NAME}} placeholders filled; output scrubbed.
sec runRun a command with NAME injected as an env var; output scrubbed.
sec genMint a password or token straight into the vault and a .env — never displayed.
sec whereEvery placement and recent use of a secret. The compromise-day question.
sec rotateNew value → re-pushed to every placement → manual steps listed honestly.

The rest — init · ls · env · render · import · export · place · recipients · identity · cert · audit · rm · get · skill — are in the docs. sec cert also does local TLS (CA, issue, self-signed) with keys written 0600, because a dev cert is a credential that usually ends up world-readable in /tmp.

the harness, not the model

One command installs the skill and the deny rules.

sec skill install
$ sec skill install
# symlinks skills/sec → ~/.claude/skills and ~/.agents/skills, then merges into
# ~/.claude/settings.json → permissions.deny:
  Read(~/.config/sec/**)     # the vault and the identity
  Read(**/.env*)             # the files sec writes for you
  Bash(sec get:*)            # the print path
  Bash(sec export:*)         # the bulk print path

This is the same shape AWS now recommends for agents — a harness-level hook that blocks the read-the-value call outright — except it's four lines in a settings file and works for any credential, not one cloud's. The model is never asked to be trustworthy about it.

threat model, honestly

What this does not defend against.

sec defends against sloppiness and logs — secrets in transcripts, guides, commits, test output, screen-shares, chat.

It does not defend against a hostile agent with network access. Such an agent could curl a value to a webhook through exec — and so could every other tool in this category, including the ones that don't say so. What sec adds is that the silly attempt is visible: an audit line names the secret, the command and the agent. Visible, not impossible. Anyone promising otherwise is selling you a proxy and a dashboard.
